# Cinema API · MongoDB

Серверна частина кінотеатру: фільми, зали, розклад сеансів і бронювання місць. Побудована на NestJS, дані зберігаються в MongoDB через Mongoose.

Це продовження домашнього завдання №2: зовнішня поведінка маршрутів лишилася тією самою, змінилися сховище й спосіб гарантувати, що одне місце не продається двічі. Нове:

- три колекції `films`, `halls`, `showings`; таблиці `bookings` і `booking_seats` зникли, їхній вміст живе всередині документа сеансу;
- бронювання й скасування виконуються **одним оновленням одного документа**, без транзакцій;
- ідентифікатори мають формат ObjectId; некоректний формат дає `400`, неіснуючий документ — `404`;
- у відповідях `id` завжди рядок, внутрішнє `_id` назовні не потрапляє.

## Встановлення

Потрібні Node.js 22.12 або новіший і Docker.

```bash
npm install
```

## Змінні середовища

Створіть файл `.env` у корені проєкту, наприклад скопіюйте зразок командою `cp .env.example .env`:

```dotenv
PORT=3000
MONGO_PORT=27018
MONGODB_URI=mongodb://localhost:27018/cinema
```

| Змінна        | Опис                                              | Обов'язкова        |
| ------------- | ------------------------------------------------- | ------------------ |
| `PORT`        | Порт, на якому слухає сервер                      | ні, типово `3000`  |
| `MONGODB_URI` | Рядок підключення до MongoDB                      | так                |
| `MONGO_PORT`  | Порт MongoDB на хості (використовує Docker Compose) | ні, типово `27017` |

Змінні проходять валідацію класом `EnvironmentVariables` ([src/config/env.validation.ts](src/config/env.validation.ts)) через `ConfigModule`: якщо `MONGODB_URI` бракує або він не починається з `mongodb://`, застосунок не стартує. Підключення створює `MongooseModule.forRootAsync`, який бере рядок з `ConfigService`. Порт `27018` обрано, щоб не конфліктувати з іншим MongoDB на `27017`.

## Запуск

Підняти MongoDB через Docker Compose:

```bash
docker compose up -d
```

(або `npm run db:up`, що дочікується готовності контейнера)

Заповнити базу тестовими даними: 2 фільми, 2 зали, 4 сеанси в різні дати, 1 бронювання. Скрипт розрахований на порожню базу; повторний запуск не створює дублікатів, бо кожен документ має фіксований `_id` і записується як upsert з `$setOnInsert`:

```bash
npm run seed
```

Запустити застосунок у режимі розробки:

```bash
npm run start:dev
```

Swagger-документація: <http://localhost:3000/docs> (JSON — `/docs-json`).

Інші команди:

```bash
npm run build       # збірка
npm run start:prod  # запуск зібраної версії
npm run lint        # oxlint
npm run test:e2e    # e2e-тести на окремій базі cinema_test
npm run db:down     # зупинити контейнер
```

## Перевірка запитами

Файл [requests.http](requests.http) виконується згори вниз розширенням REST Client для VS Code. Він створює фільм, зал, сеанс і бронювання, а потім проходить кожну помилку з опису маршрутів. Ідентифікатори підставляються зі змінних (`{{createFilm.response.body.id}}` тощо), очікуваний код відповіді вказаний у заголовку кожного запиту.

## Маршрути

| Метод    | Шлях                      | Успіх | Помилки            |
| -------- | ------------------------- | ----- | ------------------ |
| `POST`   | `/films`                  | 201   | 400                |
| `GET`    | `/films`                  | 200   |                    |
| `GET`    | `/films/:id`              | 200   | 400, 404           |
| `PATCH`  | `/films/:id`              | 200   | 400, 404           |
| `DELETE` | `/films/:id`              | 204   | 400, 404, 409      |
| `POST`   | `/halls`                  | 201   | 400, 409           |
| `GET`    | `/halls`                  | 200   |                    |
| `GET`    | `/halls/:id`              | 200   | 400, 404           |
| `DELETE` | `/halls/:id`              | 204   | 400, 404, 409      |
| `POST`   | `/showings`               | 201   | 400                |
| `GET`    | `/showings`               | 200   | 400                |
| `GET`    | `/showings/:id`           | 200   | 400, 404           |
| `GET`    | `/showings/:id/seats`     | 200   | 400, 404           |
| `POST`   | `/showings/:id/bookings`  | 201   | 400, 404, 409      |
| `GET`    | `/showings/:id/bookings`  | 200   | 400, 404           |
| `GET`    | `/bookings`               | 200   |                    |
| `DELETE` | `/bookings/:id`           | 204   | 400, 404           |

`GET /showings` приймає `filmId`, `date` (`YYYY-MM-DD`, доба за UTC), `page` (від 1, типово 1), `limit` (1–100, типово 20), `sort` (`asc`/`desc`, типово `asc`) і повертає `{ items, total, page, limit }`. Фільтр, сортування `{ startsAt, _id }`, `skip`/`limit` і `countDocuments` виконуються запитом до MongoDB; назви фільму й залу підставляє `populate`.

Усі помилки мають структуру `{ statusCode, message, error, path, timestamp }`.

## Модель даних

```text
films     { _id, title, durationMinutes, releaseYear }
halls     { _id, name (unique), rows, seatsPerRow }
showings  { _id, film → films, hall → halls, startsAt, price,
            seats:    [ { row, seat, bookingId | null } ],
            bookings: [ { _id, seats: [ { row, seat } ], totalPrice, createdAt } ] }
```

Кожна колекція описана класом з `@Schema`/`@Prop` у теці `schemas` свого модуля, вкладені документи (`ShowingSeat`, `Booking`, `BookedSeat`) — окремими класами зі своїми схемами. Обов'язкові поля позначені `required`, цілі додатні числа перевіряє валідатор схеми, назва залу має унікальний індекс. Моделі підключаються у feature-модулях через `MongooseModule.forFeature`. Ціни зберігаються цілими числами в копійках.

Перелік місць залу не зберігається в документі залу: його обчислює сервіс з `rows` і `seatsPerRow`. Під час створення сеансу цей перелік копіюється в масив `seats` сеансу, і кожне місце отримує `bookingId: null`.

### Чому місця й бронювання лежать усередині документа сеансу

Бронювання складається з двох дій: позначити місця зайнятими й зберегти запис бронювання. У PostgreSQL обидві дії виконувала одна транзакція, а подвійний продаж відсікав унікальний індекс. У MongoDB оновлення **одного** документа неподільне саме по собі, а зміна кількох документів однією операцією вимагає транзакції, яка, своєю чергою, вимагає replica set.

Якщо місця й бронювання лежать усередині сеансу, обидві дії стають одним `updateOne`:

```ts
showingModel.updateOne(
  // фільтр збігається, лише поки КОЖНЕ потрібне місце вільне
  { _id, $and: seats.map(({ row, seat }) => ({ seats: { $elemMatch: { row, seat, bookingId: null } } })) },
  // займаємо місця й додаємо бронювання в тому ж оновленні
  { $set: { 'seats.$[target].bookingId': bookingId }, $push: { bookings: booking } },
  { arrayFilters: [{ $or: seats.map(({ row, seat }) => ({ 'target.row': row, 'target.seat': seat })) }] },
);
```

`matchedCount === 0` означає, що хоча б одне місце вже зайняте: документ не змінився, сервіс відповідає `409`. Два одночасні запити на те саме місце виконаються послідовно, і другий отримає `matchedCount = 0` — це перевіряє e2e-тест із п'ятьма паралельними бронюваннями. Читання документа з подальшою перевіркою в коді й записом не використовується, бо між читанням і записом інший запит міг би зайняти місце.

Дві перевірки виконуються **до** оновлення, бо фільтр їх не розрізняє:

- місце поза схемою залу (`row > rows` або `seat > seatsPerRow`) — інакше воно дало б `409` замість `400`;
- повтор однієї пари `row`/`seat` у запиті (`@ArrayUnique` у DTO) — інакше дві однакові умови задовольнилися б одним вільним місцем, і в `bookings` потрапив би запис на одне крісло з подвійною ціною.

Скасування також одне оновлення: сеанс шукається за вкладеним `bookings._id` (на нього є індекс), `$set` повертає `bookingId: null` місцям з цим id, `$pull` видаляє запис з `bookings`.

Межа застосовності: вкладення підходить, бо кількість даних обмежена. Місць у залі сотні, бронювань на сеанс не більше, ніж місць, тож документ сеансу не росте безмежно (ліміт документа — 16 МБ). Якби записи накопичувалися без обмеження (наприклад, історія за роки), окрема колекція була б правильнішою.

Масив `seats` — джерело істини про зайнятість (`GET /showings/:id/seats` обчислює `isBooked` з `bookingId`). Перелік місць у бронюванні його дублює, щоб віддати бронювання без перебору всіх місць залу. `GET /bookings` збирає вкладені бронювання з усіх сеансів агрегацією `$unwind` + `$replaceRoot`.

### Зв'язки без зовнішніх ключів

MongoDB не має зовнішніх ключів, тому сервіс перевіряє їх сам: перед створенням сеансу — що фільм і зал існують (`400`, якщо ні), перед видаленням фільму чи залу — що на нього не посилається жоден сеанс (`409`).

## Перевірки

- **Форма вхідних даних** — DTO з декораторами `class-validator`, `ValidationPipe` зареєстрований глобально (`whitelist`, `transform`).
- **Формат ідентифікаторів** — `ParseObjectIdPipe` для параметрів маршруту й `@IsMongoId` для `filmId`/`hallId` у тілі та query. Перевіряється рядок з 24 шістнадцяткових символів до звернення до бази (`Types.ObjectId.isValid` не використовується, бо приймає будь-який рядок з 12 символів).
- **Доменні правила, що потребують стану бази** — у сервісах: існування фільму й залу, межі залу, вільні місця, залежні сеанси, унікальна назва залу (`409` за кодом помилки `11000`).
- **Відповіді** — класи DTO (`FilmResponseDto`, `HallResponseDto`, `ShowingDetailsDto`, `BookingResponseDto` …) перетворюють документ на відповідь з рядковим `id`.
